vinext 1.1 is out, ten days after [1.0](/blog/vinext-1-0).

1.0 got caching to store the right things. 1.1 is about what happens after something changes: when you call `revalidateTag()`, when a `"use cache"` entry goes stale, or when a page calls `notFound()` halfway through a render. In each case vinext now does what Next.js does, which mostly means your users wait less.

To upgrade:

```sh
npm install vinext@1.1.0 @vinext/cloudflare@1.1.0
```

If you run Workers Response Store in its default service-binding mode, deploy the Response Store Worker as well as your app (`deploy:response-store` in projects generated by `vinext init`), so both sides pick up the new invalidation API.

## `revalidateTag()` no longer makes everyone wait

This is the change most apps will notice.

In Next.js, `revalidateTag(tag, "max")` doesn't throw cached pages away. It marks them stale. The next visitor gets the cached version straight away, and the page regenerates in the background. Only an explicit `expire: 0` forces a hard expiry.

On Cloudflare, vinext used to purge instead. Every page with that tag became a blocking cache miss, so the first visitor after a content update paid for a full render, and on a busy tag that could mean a lot of renders at once.

1.1 fixes this on both Cloudflare backends:

- **Workers Cache** uses its new soft invalidation (`ctx.cache.invalidate()`). Matching entries are marked stale, and the edge keeps serving them while it fetches a fresh copy from your Worker in the background.
- **Workers Response Store** marks matching entries stale in its metadata and in R2, instead of eagerly regenerating every one of them. They're served stale and revalidated on their next read, and stop being served once their `expire` passes. This also fixes data entries that couldn't be replayed, which previously weren't invalidated at all.

```ts
"use server";

import { revalidateTag } from "next/cache";

export async function publishPost() {
  // ...save the post...
  revalidateTag("posts", "max"); // serve stale, regenerate in the background
}
```

Hard purges still happen wherever Next.js semantics need them.

## `"use cache"` serves stale too

The same idea applies inside a render. Before 1.1, a `"use cache"` function past its `revalidate` time was recomputed before the response could continue, so every request after the deadline paid the full cost of the function. Now the stale value is returned immediately and the entry regenerates in the background through `waitUntil`, as Next.js does. Entries past their `expire` are regenerated rather than served.

Cache keys are also more accurate. vinext now uses React's Flight serialization of the arguments for cache identity and replay, the same approach Next.js uses, and hashes them synchronously so a hit can resolve before the shell is flushed.

## ISR stores what Next.js stores

We keep finding small cases where vinext's cached output differed from Next.js's. 1.1 closes a batch of them:

- A page that calls `notFound()`, `redirect()`, `forbidden()` or `unauthorized()` is now stored in the ISR cache with its real status (and `location` for redirects), and served from the cache on later requests. Unmatched 404s are never cached.
- A special error caught inside a `<Suspense>` boundary streams as a `200`, as Next.js does.
- Pages that may be stored now get their generated metadata (`<title>`, canonical links, robots tags) in `<head>`, including pages regenerated or warmed by Response Store and Workers Cache. Crawlers that only read the head now see the right tags.
- With the opt-in build prerender, pages whose special error escapes the shell are written at build time with their status, instead of failing the route or being skipped.

## Faster client navigations

Until now, every client-side navigation ran your page component twice: once in a probe outside React to catch redirects early, then again for the actual RSC render. Any data fetching in the page ran twice, one after the other, and the first run had no React `cache()` scope. In 1.1 the probe is gone for RSC requests. Redirects and `notFound()` reach the client router through the Flight payload, which is how Next.js handles them.

Related fixes:

- React `cache()` is now shared between `generateMetadata()` and the page render, so a function wrapped in `cache()` runs once per request instead of twice.
- `vinext start` compresses RSC responses. It used to compress HTML but send `text/x-component` uncompressed, so every navigation and Server Action response went out at full size. Compression now follows the same rules as `next start`.
- Client disconnects now abort `request.signal`, so long-running work can stop when nobody is waiting for it.
- Libraries like next-intl that store request state in `cache()` no longer accidentally mark a page as dynamic, so those pages prerender and cache as they do with `next build`.

## Smaller fixes worth knowing about

- `redirect()` from a page reached through a prefetched `<Link>` is now followed correctly.
- Intercepting routes resolve through proxy rewrites and authorize the interception source like a direct request.
- Repeated slashes and backslashes in URLs redirect the way Next.js does.
- `/_next/image` responses send `x-nextjs-cache` and `x-vinext-cache` headers.
- A function-form `next.config` receives the real `defaultConfig`.
- Cached font CSS no longer embeds the file path of your checkout.
- The dev server stays up when a request body is cancelled.
