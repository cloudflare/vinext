To upgrade, bump both packages:

```sh
npm install vinext@1.1.0 @vinext/cloudflare@1.1.0
```

If you use Workers Response Store in its default service-binding mode, deploy the Response Store Worker as well, because this release calls a new invalidation API on it. In projects generated by `vinext init`, that's `deploy:response-store`.

## Faster builds and dev startup

Every merge to `main` runs the same benchmark. A 33-route App Router app is built and started with Next.js 16 (Turbopack) and with Vinext, on the same CI machine, in the same job. The results are on the [benchmarks page](/benchmarks).

The CI machines vary a lot between runs, so raw timings jump around. Comparing Vinext against the Next.js run from the same job is more reliable, and that comparison moved a lot between 1.0 and 1.1:

- **Production builds** went from about 17% faster than Next.js to about 27% faster. On the same machine, that's roughly an eighth less time spent building.
- **Dev server cold start** went from about 34% slower than Next.js to about 11% slower. Part of that comes from a change to the benchmark itself, which now starts Vinext through the project's own Vite+ instead of a global CLI. The rest is Vinext doing less work at startup.

So Vinext's dev server is still a little slower to start than Turbopack on this app. We're working on it, and we've added a much larger Pages Router app to the benchmarks so we can see where startup time goes at scale.

Most of the speedup came from a run of small PRs in the 1.0.1 patch. Each one removed work that didn't need doing:

- not running `vite-plugin-commonjs` on modules it never rewrites;
- skipping stylesheet processing and unused source maps in scan builds;
- not parsing modules that have nothing to rewrite;
- keeping heavy server modules out of the graph when only a small helper was needed.

[@h-a-n-a](https://github.com/h-a-n-a) dug into a dev cold-start regression and fixed two of these. [@jantimon](https://github.com/jantimon) fixed a regex that could backtrack badly on Pages Router modules.

## `revalidateTag()` without the wait

Here's what used to happen on Cloudflare. You publish a post, a Server Action calls `revalidateTag("posts", "max")`, and every page tagged `posts` gets purged. The next visitor to each of those pages waits for a full render, and on a busy site that's a lot of renders landing at once.

Next.js doesn't do that. A tag revalidated with a profile like `"max"` is marked stale instead. Visitors keep getting the cached page while a fresh one renders in the background. Only `expire: 0` actually throws the cache away.

Vinext now does the same on both Cloudflare caches. Workers Cache now has a soft `invalidate()` next to `purge()`. It marks entries stale, and the edge keeps serving them while it fetches fresh copies. Workers Response Store marks matching entries stale in its metadata and in R2, and they revalidate on their next read. While fixing this we also found data entries that Response Store couldn't regenerate, which meant they had never been invalidated at all. Now they are.

`"use cache"` got the same treatment. A stale entry used to be recomputed before the response could carry on, so every request after `revalidate` paid the full cost of the function. Now you get the stale value straight away, and the function reruns in the background.

## Your page renders once per navigation, not twice

This one's a bit embarrassing. Until now, every client-side navigation ran your page component twice. Vinext called the page once outside React to catch an early `redirect()` or `notFound()`, threw the result away, then rendered it for real. Your data fetching ran twice, one after the other, and the first run didn't even have React's `cache()` to share results.

That extra run is gone for navigations. Redirects and `notFound()` now reach the client router inside the RSC payload, which is how Next.js handles them.

Layouts had a similar problem. [@justYu2001](https://github.com/justYu2001) reported that next-intl's `setRequestLocale()` was being lost because Vinext also ran layouts outside `cache()` first. Without the locale, next-intl fell back to reading `headers()`. That made perfectly static pages look dynamic, so they were never prerendered or cached. Now only the real render decides whether a page is dynamic.

`generateMetadata()` and the page also share one React `cache()` now, so a cached lookup that both of them use runs once per request.

## Compressed RSC responses

[@jgeurts](https://github.com/jgeurts) noticed that `vinext start` gzipped HTML but sent RSC payloads (`text/x-component`) uncompressed. That covered every client navigation and every Server Action response. [@Adnan-Husayn](https://github.com/Adnan-Husayn) fixed it by porting the rules from Next.js's own compression middleware, so what gets compressed now matches `next start`.

## Everything else

Vinext also caches what Next.js caches in a few more places:

- A page that calls `notFound()`, `redirect()`, `forbidden()` or `unauthorized()` is cached with its real status. Unmatched 404s never are.
- Pages that might be cached get their `<title>` and other generated metadata in `<head>`, including pages rendered by Response Store and Workers Cache in the background.

There are some routing fixes too:

- A prefetched `<Link>` now follows a page's `redirect()`.
- Intercepting routes work through proxy rewrites.
- Repeated slashes in a URL redirect the way they do in Next.js.
- The dev server no longer falls over when a request body is cancelled.
