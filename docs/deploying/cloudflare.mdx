> The native Cloudflare integration is the most complete deployment target. It runs App Router server code in workerd and supports Workers bindings directly in your application.

## 1. Configure the project

<PackageManagerCommand
  commands={{
    pnpm: "pnpm dlx vinext init --platform=cloudflare",
    npm: "npx vinext init --platform=cloudflare",
    yarn: "yarn dlx vinext init --platform=cloudflare",
    bun: "bunx vinext init --platform=cloudflare",
    vp: "vpx vinext init --platform=cloudflare",
  }}
/>

The initializer creates or updates `vite.config.ts` and creates `cloudflare.config.ts`, then lets you choose caching and image optimization. It installs `cf` and Cloudflare Vite plugin v2 and generates scripts for `vite dev`, `vite build`, `vite preview`, and `vinext-cloudflare deploy`. Commit the source config files; the generated Cloudflare Build Output stays gitignored.

Response Store service-binding mode declares its second Worker in the typed config and builds both Workers together. KV namespaces and missing Response Store R2 buckets are automatically provisioned on deployment. See [Caching on Cloudflare](/docs/guides/caching) for each adapter's config.

For TypeScript projects, add `.cloudflare/types` to the `include` list in `tsconfig.json`. The plugin generates binding and runtime declarations there during development and builds; these files stay gitignored. Run `cf workers types` to generate them before a standalone type-check without building the app.

## 2. Authenticate

<PackageManagerCommand

    bun: "bunx cf auth login",

Set `accountId` at the top level of `defineConfig` in `cloudflare.config.ts` (outside `worker`), or set `CLOUDFLARE_ACCOUNT_ID`. In CI, use a `CLOUDFLARE_API_TOKEN` instead of browser login.

## 3. Deploy

<PackageManagerCommand
  commands={{
    pnpm: "pnpm dlx @vinext/cloudflare deploy\npnpm dlx @vinext/cloudflare deploy --env staging",
    npm: "npx @vinext/cloudflare deploy\nnpx @vinext/cloudflare deploy --env staging",
    yarn: "yarn dlx @vinext/cloudflare deploy\nyarn dlx @vinext/cloudflare deploy --env staging",
    bun: "bunx @vinext/cloudflare deploy\nbunx @vinext/cloudflare deploy --env staging",
    vp: "vpx @vinext/cloudflare deploy\nvpx @vinext/cloudflare deploy --env staging",
  }}
/>

The deploy command validates the initialized setup, builds all Vite environments, and deploys the application Worker's Build Output using `cf`. `--env staging` selects the staging Vite mode; `--preview` selects the preview mode.

For Response Store service-binding mode, build and deploy the cache Worker explicitly before the first application deployment:

```sh
pnpm run build:vinext
pnpm run deploy:response-store
pnpm run deploy:vinext
```

`create-vinext-app` uses `build` and `deploy` instead of `build:vinext` and `deploy:vinext`. Redeploy the Response Store when its package or config changes; normal application deployments do not redeploy it.

To prefill configured caches before promoting a new Worker version, see [Cache warming](/docs/guides/caching#cache-warming).

## Use Workers bindings

Import `env` from `cloudflare:workers` in Server Components, Route Handlers, and Server Actions. Configure each binding in the Worker's `env` object in `cloudflare.config.ts`.

```tsx
import { env } from "cloudflare:workers";

export default async function Page() {
  const posts = await env.DB.prepare("SELECT * FROM posts").all();
  return <pre>{JSON.stringify(posts.results)}</pre>;
}
```

See Cloudflare's [bindings documentation](https://developers.cloudflare.com/workers/runtime-apis/bindings/) for product-specific configuration, and the [Workers Vite plugin documentation](https://developers.cloudflare.com/workers/vite-plugin/) for the underlying development environment.

## Middleware and static files

Workers Static Assets serves files from `public/` and the `/_next/static` build output before the Worker runs, so middleware does not run for them. In Next.js, middleware runs for every path its `matcher` matches, including public files. Serving them without the Worker skips an invocation and its latency for every script, stylesheet, font, and image.

Every file in `public/` can be fetched by anyone who knows its URL. Serve content that needs authentication from a Route Handler or page instead. To run middleware before specific public files, route their paths through the Worker with `runWorkerFirst` in `cloudflare.config.ts`:

```ts
defineWorker({
  // ...existing Worker settings
  assets: {
    // ...existing asset settings
    runWorkerFirst: ["/downloads/*"],
  },
});
```

Requests matching these patterns run middleware first, then vinext serves the file through the `ASSETS` binding. To run middleware before every public file, as Next.js does, route everything except the build output:

```ts
runWorkerFirst: ["/*", "!/_next/static/*"],
```

Keep the `/_next/static/*` exclusion, prefixed with `basePath` if one is set. vinext serves the build output only from Workers Static Assets, so `runWorkerFirst: true` makes the app's scripts and stylesheets return 404. When the [Static Assets response cache](/docs/guides/caching#static-assets-response-cache) is configured, list only positive patterns and include `/_vinext/static-cache/*`.
