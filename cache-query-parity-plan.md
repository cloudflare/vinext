# App Router query-string cache parity: mini plan

**Goal:** Share completed static/ISR App Page responses across _user_ query strings, as Next.js does, without sharing query-dependent output. Preserve protocol response variants and keep the Workers Cache and Workers Response Store adapters separate. This covers completed responses, not PPR/Cache Components shells.

1. **Pin down the Next.js contract.** Port the relevant cases from `test/e2e/app-dir/searchparams-static-bailout/`, `test/e2e/app-dir/ppr-full/`, and `test/e2e/app-dir/custom-cache-control/` in the local Next.js reference. Add routes to the existing `examples/response-store-demo` app, so each adapter runs the same cases. Distinguish default App Page `searchParams` from `dynamic = 'force-static'` (empty values), `dynamic = 'error'` (reject dynamic access), `force-dynamic`, and client-only `useSearchParams` inside Suspense (static server shell, current-query client UI). Extract these route-config decisions at runtime as we already do for `force-dynamic`; do not apply a blanket veto to force-static's substituted empty values.
2. **Track query use without conflating admission models.** Observe server Page and metadata `searchParams` access even for an empty query. If a completed render never reads the tracked query input and has no other dynamic dependency, **that completed artifact is query-independent**; the Response Store can decide whether to persist it after rendering. This observation alone is not a pre-request guarantee for a _future streaming render_ in Workers Cache. Recheck completed Response Store writes and regeneration; never replace a shared artifact with query-dependent bytes, and match Next.js's static-to-dynamic error behavior where applicable. Query dependence through rewrites, middleware, or other request APIs must be handled at their own boundary.
3. **Workers Response Store:** For ordinary eligible App Page ISR, look up the canonical pathname-and-representation key once. On a miss, render with the original query; after completed-render admission, `put` the query-independent artifact or skip the `put` for a default query-dependent response. A streamed direct-RSC foreground miss may already have sent its conservative private, revalidate-only policy before its SSR verifier resolves; it must not publish a shared entry. For an **explicitly public dynamic** response, preserve Next.js's configured public cache policy and select a full-query key from the known policy before lookup; never overwrite that policy with `no-store` just because the page reads the query. No pre-lookup query-independence manifest and no second cache lookup are needed. Include first-visit ISR paths (for example, `generateStaticParams() { return [] }`).
4. **Workers Cache:** Its gateway must select the cached entrypoint URL and `ctx.props` before a hit, and a miss must keep streaming rather than buffer the whole response to decide cacheability. Extend the build-time cacheability manifest with a conservative query-independence decision for each resolved App Page path/route and representation, accounting for extracted `force-static`, `error`, and `force-dynamic` config. Only a manifest-certified response may use the pathname-and-representation key. Keep the original query available to the renderer on misses; an unproven route must not publish shared cache headers or be promoted by a single successful runtime probe. Explicitly public dynamic responses retain their full-query key and configured policy. Resolve query-conditional rewrites/proxy decisions before key selection or bypass caching. Define how first-visit ISR paths and regeneration obtain sufficient manifest proof; where that cannot be established without sacrificing streaming, fail closed and document the extra misses versus Next.js instead of claiming parity. Do not rely on a late stream error or `no-store` discovered after headers to retract an unsafe insertion.
5. **Preserve cache layers and variants.** Ignore user query values only for eligible completed page artifacts. Preserve HTML versus RSC, navigation versus prefetch, router-state and interception distinctions in the cache key (or a verified equivalent representation selector); Next.js currently uses `_rsc` as a CDN variant discriminator. Do not change the query-sensitive keys of Fetch Cache or `"use cache"`, or conflate App Pages with Pages Router and Route Handler policies.

   A direct Client Page RSC payload can serialize the query prop without reading it during the render. Therefore its outer adapter key remains full-query unless the payload is explicitly query-neutral; a query-bearing variant must also bypass the inner pathname-only ISR RSC entry. This does not prevent the separately rendered HTML representation from sharing after its completed-render proof.

**Regression gate:** Use those demo routes in the existing E2E suites for Workers Cache, Workers Response Store (both modes), and KV; add no new app or fixture. Cover empty-query → query and the reverse; distinct user queries; repeated query-dependent renders; shared static hits; on-demand ISR and regeneration; force-static/error/dynamic modes; explicitly public full-query HITs; query-conditional rewrites/proxy and path params; HTML/RSC/prefetch/interception separation; and client hydration with the current query. For Workers Cache, also assert that misses still stream, manifest-unknown paths cannot populate the shared key, and late `searchParams`/metadata use or stream failure cannot poison it. Assert returned content, cache policy, and HIT/MISS/BYPASS. Keep existing Pages Router, GET Route Handler, Fetch Cache, and `"use cache"` query behavior intact. Run focused unit and Miniflare E2E suites, then exact-head CI and deployed Workers Cache checks. Keep the PR draft until those pass and independent review findings are addressed.

## Client Page follow-up: implementation plan

This section refines the earlier general rule for a `"use client"` App Page. Next.js tests that reading the Page's `searchParams` makes the page dynamic and _not_ reading it leaves the page static (`test/e2e/app-dir/searchparams-static-bailout/searchparams-static-bailout.test.ts`). Its `ClientPageRoot` creates tracked values when the Client Page executes (`packages/next/src/client/components/client-page.tsx`); mere serialization of the Page's props in the RSC stream is not the observation we need. Next.js with Cache Components also has a mode in which the Client Page gets its query from router context, whereas the legacy path passes the query in RSC props. We must explicitly test rewrite semantics before adopting a context-based representation.

1. **Reproduce first, in existing suites.** Add Client Pages in `examples/response-store-demo`: one that ignores `searchParams`, one that reads it with `use(searchParams)`, one using synchronous access, and a Server Page that passes the promise into a Client Component. Run the existing Workers Cache, Response Store (both modes), and KV tests against the same routes. For HTML and direct RSC, test empty-query first and query-first, two distinct queries, repeated requests, body identity, response policy, and actual HIT/MISS/BYPASS. Inspect the Next.js reference behavior for direct RSC-only requests before declaring parity.
2. **Undo the Response Store regression.** Remove the unconditional default Client Page `BYPASS`/`no-store` branch in `response-store-adapter.worker.ts`. A route's `"use client"` directive does not by itself forbid caching. Keep a full-query key when a representation cannot yet be proved safe to share; explicit-public dynamic responses keep their full-query key and configured policy. Do not add a second lookup.
3. **Move the Client Page observation to SSR execution.** Add a thin Client Page boundary that constructs a tracked thenable in the SSR environment from the request navigation context, forwards it to the actual Page, and reports `await`, `use()`, synchronous property access, enumeration, and `useSearchParams()` via the existing SSR-to-RSC completion signal. Track the empty query identically. Do not report constructing the prop or React serializing the boundary as a read. A default completed render that observes query use or other dynamic input is not inserted under the shared key. For `dynamic = 'error'`, reject an HTML SSR-side Client Page read independently of whether the response is a shared-cache candidate; test both empty and populated queries on an on-demand path. An unverified direct RSC response must remain private and skip inner ISR as well as outer adapter storage even for an empty query. Regeneration must obey the same admission checks and static-to-dynamic rules.
4. **Require a query-neutral payload for sharing.** In the eligible shared representation, RSC must not serialize the first requester's raw query into Client Page props; HTML must not embed that query-bearing Flight payload or bootstrap state either. The Client Page boundary reads the actual query from SSR navigation context for first render and current router state in the browser. Verify initial HTML, hydration, navigation, direct RSC, and browser refresh. Preserve `force-static`'s empty query. If the browser URL and resolved/rewrite query differ, use query-sensitive identity until the exact rewritten-query semantics can be preserved.
5. **Response Store: runtime-only RSC decision.** Do **not** consult the build-time cacheability manifest, prerender artifact, or any pre-lookup query-independence certificate. An eligible App Page HTML or RSC request makes exactly one lookup under a pathname-and-representation key. On a miss, render with the original query and hold the store admission until all relevant work completes. A direct RSC render does not execute Client Components—not only a Client Page but also nested components that may call `useSearchParams()`—so tee the _same_ Flight stream into an SSR validation branch on **every eligible RSC miss**; drain its output and merge its dynamic/query observations with the RSC render's observations. The foreground Flight stream may continue to the client, but `put` happens only after both branches finish successfully, prove query-neutral bytes, and resolve a cacheable policy. If SSR observes the Page prop or `useSearchParams()`, or any branch fails/uses other dynamic data, return the request's result without publishing a shared entry. On a hit, serve only a previously admitted query-neutral representation. Regeneration must repeat the same verification before replacing an entry. This adds SSR work on a cold RSC miss, **not** a second Response Store lookup; it is not a build-time certificate. Explicit-public dynamic responses continue to use a full-query key and their configured policy.
6. **Workers Cache: build proof, pre-lookup and streaming.** Only this adapter may use a build-time cacheability certificate. During staged deployment, probe the completed HTML artifact and separately probe its paired direct RSC artifact on the staged Worker. The RSC probe must SSR its Flight stream to detect Client Component query use before classifying it. Record both static certificates for the exact resolved pathname only when both completed probes prove the relevant static representation; a single successful HTML probe never certifies RSC. An eligible Client Page RSC request may canonicalize the cached entrypoint URL _and_ `ctx.props` before its single cache lookup only when those paired certificates exist. Carry the original query only to the cold renderer, as today. Unknown paths and unproved variants remain query-sensitive and streaming; no post-header reversal or response buffering. Query-changing rewrites remain unshared.
7. **Retain all other boundaries.** Do not conflate HTML/RSC, navigation/prefetch/router-state/interception variants, dynamic pathname values, query-changing rewrites, user-specific headers/cookies, explicit-public cache policy, Pages Router, Route Handlers, Fetch Cache, or `"use cache"`. KV direct-RSC responses retain their full-query identity and may serialize the current query: verify isolation, not cross-query body equality. Avoid claiming PPR/Cache Components shell parity when only completed response parity has been implemented.
8. **Verification and review.** Run focused unit and demo E2E tests, both Response Store modes, Workers Cache Miniflare and deployed-preview cases, then exact-head CI. Exercise direct-RSC stale regeneration, nested Client Component query reads, and the `dynamic = 'error'` Client Page case in the existing demo. Have independent reviewers check Next.js parity, cache leakage, RSC hydration, and maintainability; address in-scope findings. Request Big Bonk with its explicit eight-minute completion limit after the head is green. Keep PR #3390 draft; split a cohesive boundary/payload change into a stacked PR if the cumulative diff becomes unwieldy.

**Acceptance criterion:** A Client Page that ignores `searchParams` must not be blanket-uncacheable: two user queries should reuse the same static HTML **and direct RSC** artifact, with the current browser query remaining correct. A Client Page that reads the Page prop must never publish a query-dependent response under a shared key. Response Store must establish this from a completed runtime RSC + Client Page SSR observation on a miss, with no build certificate and no second cache lookup; Workers Cache must require exact-path build proof and keep streaming. Document the limitation of any single-render staticness observation for arbitrary future query-conditional code, rather than claiming a mathematical guarantee or unqualified Next.js parity.

**Known parity boundary:** In legacy Next.js, a Suspense-wrapped Client Component that calls `useSearchParams()` may prerender a completed static fallback HTML/RSC artifact while the browser displays its current query (`test/e2e/app-dir/app-static/app-static.test.ts`). Vinext's cold on-demand render currently observes that hook and declines shared caching, so this is a safe extra miss and different server fallback, not a cross-query leak. It needs a separate, coherent static-shell render mode for HTML and RSC; do not treat the ordinary runtime observation as a static certificate or claim this case is already covered. Keep that follow-up a separately reviewed parity slice rather than weakening this PR's admission rule.

Next.js also returns HTTP 500 for a direct RSC request to a `dynamic = 'error'` Client Page that reads `searchParams`. Vinext's separate streaming Flight and SSR environments can observe that read after the Flight status is committed. This PR keeps such an unverified Flight private and refuses its cache write, but does not claim status parity: selecting 500 from the same completed SSR observation before streaming would require buffering the Flight or a larger combined-render lifecycle change. Do not substitute a second render's observation as proof about the response being sent.
